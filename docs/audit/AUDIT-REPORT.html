THE VIEWER — Top-to-Bottom Audit & Mutation Testing

Code audit + automated mutation testing · audited at v0.72.3 · 2026-06-03

This audit was triggered by a startup hang on the preflight checks. It grew into a full sweep of the engine, an automated mutation-testing pass, and the fixing of every safe, clear-cut issue it turned up. Headline: 5 issues fixed, 3 flagged for your call, 0 critical left open. The startup hang is resolved and the route that was throwing 500s is green.

1. What I did

  • Static bug-class sweep across every engine/*.py file: orphaned imports left by the modularization, infinite-loop risks, connections opened but never closed, hang-prone full-database scans, and over-broad except blocks that could hide real errors.
  • Automated mutation testing — a new tool (engine/tests/mutate.py) that deliberately breaks one small thing at a time (a < becomes >=, a + becomes -, True becomes False) and re-runs the tests. If a test fails, the break was "killed"; if every test still passes, it "survived" — a blind spot in the tests.
  • Ran the self-contained test suites in isolation to confirm the fixes: test_patterns 9/9, test_features 21/21, test_routes 34/34, new test_procedure 22/22.

3. Fixed this pass

HIGH V-01 · Preflight hang on startup

Plain version: the startup health check was reading and verifying every page of your 3.65 GB index — fine when the database was small, but a multi-minute freeze once OCR filled it. The program wasn't broken; it was grinding through a needless full scan before letting the server start.

Fix: startup now does a millisecond open-and-read probe (can SQLite open it, is the header consistent, can it read the catalog and one real table). Databases over 512 MB automatically skip the full scan. The deep scan is still available with preflight.py --deep and is time-budgeted (20 s) so it can never hang — if it can't finish it downgrades to a warning. The watchdog and /healthz share this code, so they got faster too.

HIGH V-02 · /api/threed_refs returned 500

Plain version: the 3D→manual lookup called a helper that had moved to a new file during the v0.70 clean-up and was never re-pointed. Python couldn't find the name and the route reported a generic 500.

Fix: one import line. test_routes went from 33/1 to 34/34.

MED V-03 · procedure_feature infinite loop (found & fixed here)

Full honesty: this one I caused during the audit and then caught. The first version of the mutation tool restored the original file only at the very end of its run. The sandbox killed that run for taking too long, the end-of-run restore never executed, and it left a single broken character on disk — the tools-header line read i -= 1 instead of i += 1, which loops forever.

How it was caught: the new test_procedure.py (the parser had no test before this) hung instead of passing; a stack dump pointed at the loop; a one-line grep of the real file confirmed the bad character; I restored it. I then hardened the tool so this cannot recur — it now restores the original after every single test, keeps a .orig backup, verifies a checksum at the end, and is meant to be run on a throwaway copy. Verified: test_procedure 22/22, and the live /api/procedure_full route passes.

LOW V-04 & V-05 · Two database connection leaks

Plain version: procedure_full and threed_refs each opened a database connection and never closed it — one leaked handle per request. Harmless for a while, but over a long-running session it slowly piles up. Both now close their connection on every path (including early returns).

4. Flagged for your call (not changed)

MED V-06 · safeguard.py still runs a full quick_check

The data-protection layer (safeguard.py:140) verifies databases with the same full page-by-page scan that caused the startup hang. If it's ever pointed at the 3.65 GB live index during a verify or mirror, it will be slow in the same way. Recommendation: give it the same treatment as preflight — fast probe by default, size guard, deep scan time-budgeted. I left it alone because it's the safety layer and I'd rather you sign off before I touch it.

MED V-07 · Procedure parser is under-tested (20% mutation kill)

Of the parser's mutation points, only ~20% are currently caught by tests. Most survivors are in procedure_full (which needs a database to test) and in the "cap" limits (keep at most 24 tools, 12 warnings, 120 steps) and the step-continuation logic. Nothing is wrong today — but a future refactor could silently change behavior and no test would notice. Recommendation: add a small database-backed test for procedure_full and a few boundary assertions. I can do this on request; it raises the kill rate substantially.

LOW V-08 · Dev-environment mount tearing (not shipped code)

The development sandbox occasionally serves a torn/truncated copy of large host files. This doesn't affect your installed program at all — but it's how V-03 happened, and it's why verification here is always done against the authoritative file (via the editing tools) and confirmed on your PC with RUN-ALL-TESTS.bat, never by trusting a raw sandbox read of a big file.
